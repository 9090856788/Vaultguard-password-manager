# G5.4.2 Implementation Preflight

**Gate:** G5.4.2 - VaultItem Encryption Lifecycle
**Status:** IMPLEMENTATION AUTHORIZED
**Branch:** `tech-stack-migration`
**Baseline:** `f17104cc0a9f6ebd8faa2ce8e4771f98a5cd53e6`

## Authorization Basis

The five previously open G5.4.2 contract decisions have been explicitly
approved by the project owner:

1. Persist `VaultItem.lifecycleState` with `preparing`, `active`, and `deleted`.
2. Enforce exact metadata and encrypted-secret field allowlists.
3. Include owner-scoped restore with revision/CAS protection.
4. Approve a future encrypted history collection only as later scope; do not
   introduce it in G5.4.2.
5. Retain `websiteLogo` as bounded public metadata.

The approved contract preserves client-only Vault Master Password, KEK, VEK,
encryption, and decryption handling; server-issued item IDs; AES-256-GCM with
the G5.3 canonical AAD; owner/vault/category authorization; strict validation;
revision-based `If-Match` CAS; and no plaintext secret persistence or logging.

## G4/G5 Synchronization

The approved lifecycle has been synchronized into:

- `docs/database/database-schema.md`
- `docs/engineering/g5-condition-register.md`

The G4 schema now defines the VaultItem lifecycle and conditional encrypted
secret requirement. The G5 condition register freezes the prepare -> client
encrypt -> finalize -> active lifecycle, CAS-protected update/delete/restore,
strict allowlists, and the prohibition on introducing a history collection in
this scope.

## Preflight Findings

- Current committed `VaultItem` implementation does not yet contain
  `lifecycleState`; this is an expected G5.4.2 implementation change, not a
  contract deviation.
- Current committed `encryptedSecrets` field is unconditionally required;
  G5.4.2 must make it conditional for `preparing` records and required for
  `active` records.
- Existing G4 indexes do not require a new preparation collection or a unique
  host constraint.
- Server-issued item IDs must exist before client encryption because item ID
  participates in canonical AAD.
- No server-side vault unlock is authorized.
- No plaintext secret field, plaintext secret logging, or generic persistence
  bypass is authorized.

## Implementation Scope

G5.4.2 implementation may modify only the VaultItem lifecycle and directly
required supporting backend, validation, repository, API, and test surfaces.
It must not silently redesign G3/G4, introduce encrypted history, alter the
approved vault key lifecycle, migrate real data, or redesign the UI.

Required implementation sequence:

1. VaultItem model/lifecycle persistence contract.
2. Repository lifecycle operations and owner/CAS enforcement.
3. Validation and strict request allowlists.
4. Service/controller/routes for prepare, finalize, update, delete, and restore.
5. G5.3 envelope/AAD verification integration without server-side decryption.
6. Focused unit/integration tests, including negative security cases.
7. Independent security and code review gates.

## Mandatory Verification

Before G5.4.2 is considered complete, evidence must cover:

- cross-owner and cross-vault access rejection;
- category ownership enforcement;
- server-generated ID binding;
- preparing/finalize lifecycle correctness;
- invalid and unknown request fields rejected without echo/logging;
- malformed, unsupported, or AAD-mismatched envelopes rejected;
- stale `If-Match` conflicts;
- no last-write-wins encrypted updates;
- owner-scoped soft delete and restore;
- deleted-item access rules;
- plaintext-secret persistence/logging rejection;
- regression coverage for existing auth and G5.4.1 behavior.

Live MongoDB integration testing remains a separate environment-dependent
verification item where the existing repository test setup cannot provide it.

## Explicit Prohibitions

Do not:

- receive or derive the Vault Master Password on the server;
- unwrap the VEK on the server;
- persist raw KEK/VEK or plaintext secrets;
- add a preparation collection;
- add a unique `{ host, vaultId }` constraint;
- use last-write-wins for encrypted updates;
- introduce a plaintext history collection or field;
- bypass controller -> service -> repository -> Mongoose boundaries;
- activate real-data migration;
- commit secrets or local `.env` values;
- merge to `master`.
