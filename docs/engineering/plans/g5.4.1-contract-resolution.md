# G5.4.1 Contract Resolution

**Project:** VaultGuard Password Manager
**Branch:** `tech-stack-migration`
**Gate:** G5.4.1 - Vault Cryptographic Lifecycle
**Status:** Resolved planning contract; implementation remains separately gated
**Source plan:** `docs/engineering/plans/g5.4.1-vault-cryptographic-lifecycle.md`
**Reviewed baseline:** G3/G4 architecture, G5 blueprint and condition register,
G5.3 implementation, and `docs/security/g5.3-crypto-security-audit.md`

This artifact resolves the four open decisions in the G5.4.1 lifecycle plan.
It does not authorize production code, schema, route, test, frontend, crypto,
dependency, migration, commit, push, or merge changes.

## 1. Decision Summary

| Decision | Selected resolution |
|---|---|
| Vault ID | Server-generated MongoDB `ObjectId`; public metadata, never secret-derived; allocated before client AAD construction. |
| Server lifecycle | Use existing `migrationState` values only. Finalized vaults are `verified` after structural envelope validation and client-local preflight; `locked`/`unlocked` are never persisted server states. |
| Unlock verification | Fetch wrapped VEK metadata; derive KEK and unwrap VEK entirely in the client. No server unlock or password-verification endpoint. |
| Idempotency | Use resource-native `_id` uniqueness for creation and owner-scoped CAS with `updatedAt`/ETag for updates. Do not add a generic idempotency collection or framework. |

These decisions preserve the G3/G4 boundary. They do not make a zero-knowledge
or production-encryption claim; those claims remain subject to later gates.

## 2. Decision 1: Server-Issued Vault IDs

### Selected strategy

Vault IDs are MongoDB `ObjectId` values generated by the server. The target
model already uses MongoDB `_id: ObjectId`, and all existing target models use
Mongoose/MongoDB ObjectIds with optional `legacyId` values reserved for
migration traceability.

The server allocates the ID before the client creates the wrapped VEK envelope.
The recommended API sequence is:

```text
POST /api/v1/vaults/prepare
  -> server generates ObjectId and returns public vaultId
client derives KEK, generates VEK, wraps VEK with vaultId in AAD
POST /api/v1/vaults/:vaultId/finalize
  -> server creates the owner-scoped vault record
```

The prepare operation does not persist a plaintext key, password, envelope,
or pending vault record. It returns only the generated public identifier and
the creation contract version. The finalize operation authorizes the current
user and creates the record using the supplied server-issued ID.

The implementation must validate that `vaultId` is a valid ObjectId and that
the authenticated owner is the only source of `ownerUserId`. A client may not
choose an arbitrary ID to bypass ownership or claim another user's vault.
Because the prepare result is not secret authorization, the finalize operation
must still require authentication and must use owner-scoped create semantics.

### Rationale

- Matches the approved G4 schema and current repository convention.
- Keeps AAD deterministic because the client knows the server ID before wrap.
- Avoids deriving an identifier from the Vault Master Password or VEK.
- Keeps IDs as public selectors, not cryptographic material.
- Preserves `legacyId` for migration without using it as authorization.

### Alternatives considered

| Alternative | Decision | Reason |
|---|---|---|
| Client-generated random ObjectId | Rejected | The client would control the resource identifier and the AAD input; it is unnecessary for the approved server-owned persistence model. |
| UUID/ULID | Rejected for this gate | No existing target convention requires it; changing from ObjectId would add migration/API/schema surface without security benefit. |
| ID derived from password, salt, or VEK | Prohibited | Leaks a relationship to secret material and violates the public-ID boundary. |
| Generate ID and persist an incomplete vault first | Rejected | Current `Vault` requires wrapped key metadata and no `pending` enum exists; it risks partially active records. |
| Server-side AAD construction after receiving plaintext VEK | Prohibited | Would move key material to the server and violate G3. |

### Security and AAD implications

`vaultId` is public metadata. It may be included in canonical G5.3 AAD, but it
must never be treated as a secret or as an authorization credential. The client
uses the exact server-issued string representation in the `vek-wrap` context.
The server validates that the persisted envelope's AAD metadata is consistent
with the vault ID, key ID, revision, purpose, and version; it does not unwrap
the VEK.

### Approval requirement

This preserves G3/G4 and requires no architecture exception. Engineering Lead,
Database Engineer, and Security/Crypto Architect must confirm the endpoint
contract before implementation. No human approval is required to select a new
crypto primitive or parameter because none is introduced.

## 3. Decision 2: Vault Lifecycle States

### Selected server state model

G5.4.1 uses the existing `Vault.migrationState` enum without adding a new
schema state:

```text
finalize request accepted with valid envelope -> verified
verified -> blocked     (integrity/verification failure detected by service)
verified -> deleted     (future explicit soft-delete operation, if approved)
```

The existing `awaiting-owner`, `encrypting`, and `legacy-quarantined` states
remain available for the separately planned legacy migration workflow. They are
not used to invent a new G5.4.1 server-side lock protocol. A malformed or
conflicting finalize request is rejected and does not create a vault; it is not
silently recorded as `verified` or converted to a new state.

`verified` has a deliberately narrow meaning in this gate: the server accepted
the required metadata and envelope shape, and the client completed its local
preflight unwrap before finalization. It does **not** mean the server proved
the Vault Master Password or independently decrypted the VEK.

### Client key state is separate

The browser maintains transient states independently:

```text
locked -> unlocking -> unlocked
unlocked -> locked
unlocking -> locked       (wrong password, tamper, malformed data, timeout)
unlocked -> locked        (logout, auto-lock, session loss, explicit lock)
```

`locked` and `unlocked` are client-memory states only. They must not be stored
in `migrationState`, MongoDB, an API cookie, Redux persistence, localStorage,
sessionStorage, IndexedDB, TanStack Query cache, telemetry, or logs.

### Transitions and authorization

- `prepare`: authenticated account; no database resource is created.
- `finalize`: authenticated account; owner comes from the access-token subject;
  the server-issued ID may be finalized only for that owner and only once.
- `verified -> blocked`: service/integrity handling only, owner-scoped and
  auditable with safe metadata if audit integration is approved.
- `verified -> deleted`: not implemented by this contract; requires the
  separately approved soft-delete operation and owner-scoped CAS.
- Client lock/unlock: local browser key manager only; server authorization is
  not involved.

### Concurrency and rollback

Creation is unique on `_id`. Concurrent finalization attempts for the same
server-issued ID are handled as an idempotent replay only when the authenticated
owner and canonical request fingerprint match; otherwise they return conflict.
There is no partially persisted pending vault to roll back.

An accepted database create is not undone by deleting all collections. A failed
response is retried against the same resource ID, and the client reconciles by
fetching safe metadata. Any future state update uses owner scope and CAS.

### Alternatives considered

| Alternative | Decision | Reason |
|---|---|---|
| Persist `locked`/`unlocked` server state | Prohibited | Local key availability is not server knowledge and would create misleading security state. |
| Add `pending` to the Mongoose enum | Deferred/rejected for G5.4.1 | Current schema has no pending state; a new state needs a separate architecture/schema decision. |
| Use `awaiting-owner -> encrypting -> verified` for every create | Rejected | Those states describe migration/encryption workflow and would overcomplicate direct lifecycle creation. |
| Treat successful HTTP write as master-password verification | Rejected | The server cannot verify a password it never receives. |

### Approval requirement

The semantics of `verified` must be explicitly accepted by Engineering Lead and
Security/Crypto Architect before implementation. This is a terminology and
workflow clarification, not a G3/G4 crypto change.

## 4. Decision 3: Client-Only Unlock Verification

### Selected flow

There is no server-side unlock operation. The client verifies the entered Vault
Master Password by successfully unwrapping the authenticated VEK envelope.

1. Client sends `GET /api/v1/vaults/:vaultId/key-material` with the normal
   short-lived access token.
2. Server authenticates the account and loads the vault through an
   owner-scoped repository query.
3. Server returns the wrapped VEK envelope and public KDF/key/version metadata.
4. Client prompts for the Vault Master Password locally.
5. Client calls the existing G5.3 `deriveVaultKek(masterPassword, kdf)`.
6. Client calls the existing G5.3 `unwrapVek(envelope, kek, context)`.
7. Successful authenticated decryption returns a 32-byte VEK, which is held
   only in a transient in-memory key manager.
8. Client zeroizes temporary buffers as practical and enters `unlocked` state.

The same local sequence runs before finalize creation. The client must complete
that preflight before sending the wrapped envelope, so a client-generated
wrong-password envelope is not knowingly submitted as a valid vault. This is
a client assertion and structural server validation, not server knowledge of
the master password.

### Invalid and hostile input behavior

- Wrong password/wrong KEK: local `unwrapVek()` failure; generic
  `VAULT_UNLOCK_FAILED` client error; no password retry request.
- Tampered ciphertext, tag, nonce, or AAD: authenticated unwrap fails closed;
  client remains locked; no plaintext or key is sent to the server.
- Unsupported version/algorithm: client and server reject without downgrade;
  generic unlock failure is shown to the user.
- Malformed stored envelope: server returns typed integrity failure or generic
  not-usable-vault response without returning secret material.
- Cross-owner access: indistinguishable `404` and no envelope disclosure.

The server can learn that a user requested key metadata, the vault ID, request
timing, success/failure of metadata validation, and ordinary authorization
outcomes. It cannot learn the Vault Master Password, derived KEK, plaintext
VEK, or decrypted vault contents.

### API rule

If an API is needed for unlock, it is a metadata retrieval endpoint only. There
must be no endpoint accepting a Vault Master Password, plaintext VEK, or KEK,
and no endpoint returning a plaintext VEK.

### Alternatives considered

| Alternative | Decision | Reason |
|---|---|---|
| Server receives master password and derives KEK | Prohibited | Direct G3 violation. |
| Server receives VEK and unwraps it | Prohibited | Exposes plaintext key material and defeats the client-side boundary. |
| Server returns a boolean unlock result | Rejected | It would imply server-side verification and create an unnecessary oracle. |
| Client sends a proof of successful unwrap | Deferred | No approved proof protocol exists; local unlock is sufficient for this lifecycle slice. |

## 5. Decision 4: Idempotency and Concurrency

### 5.1 Vault creation

Creation uses the server-issued `vaultId` as the resource-level idempotency
identity. No generic distributed idempotency framework or new collection is
introduced.

The finalize request includes:

- path `vaultId` from the prepare response;
- authenticated owner from the access token;
- the complete wrapped envelope/KDF/key metadata;
- optional `Idempotency-Key` only if the final HTTP contract needs a client
  retry correlation value. It is not persisted in a new idempotency store.

The database `_id` uniqueness guarantee is authoritative:

- first valid create returns `201 Created`;
- a retry after a lost response reads the same owner-scoped resource;
- if the canonical creation payload matches, return the existing safe resource
  with `200 OK` and an idempotent-replay indicator;
- if the owner or canonical payload differs, return `409 Conflict` without
  revealing another owner's resource details.

The canonical comparison must use a server-defined normalized metadata
fingerprint, not raw secret logging or a client-trusted arbitrary hash. The
implementation may compare the stored envelope/KDF/key metadata directly in
memory under bounded sizes; it must not persist a new plaintext fingerprint.

If exact replay detection cannot be implemented without a new field or
collection, the implementation must stop and request approval rather than
pretend POST is idempotent.

### 5.2 Vault metadata updates

Metadata updates use owner scope plus `If-Match` against the current
`updatedAt` value (or an equivalent server-generated ETag derived from that
value). The existing repository already has an `expectedUpdatedAt` CAS shape.

- matching owner and version: update once and return `200`;
- stale version: return `412 Precondition Failed` or the repository's approved
  typed conflict response; do not overwrite newer data;
- retry after a lost response: client refetches and compares the desired safe
  metadata, then treats an already-applied identical update as success;
- different current value: return conflict and require user/client merge.

No update accepts client `ownerUserId`, changes immutable `_id`/owner, or
silently changes lifecycle state.

### 5.3 Wrapped-VEK replacement/update

Key metadata replacement is a future key lifecycle operation, not key rotation
implementation in this gate. If a narrowly scoped replacement endpoint is
needed for G5.4.1, it must require:

- owner-scoped vault ID;
- `If-Match` current `updatedAt`;
- expected current `currentKeyId` and encryption format version;
- a new key ID and authenticated wrapped envelope whose AAD matches the new
  key context;
- no raw KEK, VEK, or master password.

The repository updates `wrappedVekEnvelope`, `kdf`, `currentKeyId`,
`encryptionFormatVersion`, and approved state fields in one CAS operation.

After a successful update, retry behavior is safe when the persisted target
metadata is exactly the requested target; otherwise a stale request receives a
conflict. A request with an old expected key ID cannot overwrite a newer key.

### Retention and scope

There is no idempotency-record TTL because this design does not add an
idempotency collection. The server-issued ID remains the creation resource
identity, while normal vault retention and soft-delete rules apply. Request
IDs remain useful for tracing but are not authorization or idempotency proof.

### Alternatives considered

| Alternative | Decision | Reason |
|---|---|---|
| Generic idempotency collection/service | Rejected | Unnecessary for one-document resource creation and CAS updates; adds schema/retention/infrastructure scope. |
| Client timestamp as idempotency key | Prohibited | Not unique or trustworthy enough. |
| Unconditional update/retry | Prohibited | Causes lost updates and stale wrapped-VEK replacement. |
| Distributed Redis idempotency | Out of scope | Redis is deferred by G5 and not required for this lifecycle contract. |
| Delete/recreate on retry | Prohibited | Can lose ownership/state and violates safe rollback principles. |

## 7. Security Requirements and Boundary Checks

The implementation must pass all of these checks:

- Vault Master Password never appears in a request, response, URL, cookie,
  log, audit event, telemetry record, or database document.
- Plaintext VEK and KEK never reach the server or persistence layer.
- KEK derivation and VEK unwrap call only the committed G5.3 client boundary.
- Wrapped VEK is the only persisted cryptographic key representation.
- No raw key enters localStorage, sessionStorage, IndexedDB, Redux persistence,
  query cache, logs, telemetry, or error reports.
- No plaintext VaultItem secret is introduced by this lifecycle work.
- G5.3 validation, versions, algorithms, AAD, nonce, tag, and context binding
  remain unchanged.
- Owner scope is mandatory for every vault query and update.
- Cross-owner responses do not reveal resource existence.
- `locked`/`unlocked` are client-only transient states.
- The existing `503 VAULT_ENCRYPTION_NOT_READY` boundary remains for all
  functionality not explicitly integrated and reviewed.
- No zero-knowledge, end-to-end encryption, encrypted-at-rest, or production
  encryption claim is added by implementation or UI text.

## 8. Database Implications

No new collection, model, index, or plaintext field is required by these
decisions. The existing `vaults` document remains the target:

- MongoDB `_id` is the server-generated ObjectId.
- `ownerUserId` is immutable and token-derived.
- `wrappedVekEnvelope`, `kdf`, `currentKeyId`, and
  `encryptionFormatVersion` are persisted only after strict validation.
- `migrationState` uses the existing enum; new `pending`, `locked`, or
  `unlocked` values are not introduced.
- `{ ownerUserId: 1, deletedAt: 1 }` and `{ ownerUserId: 1, _id: 1 }` remain
  the approved vault indexes.
- No `{ host, vaultId }` unique index is added.

The create/finalize repository operation must use `_id` uniqueness and safe
owner projections. Key metadata replacement must use owner scope and existing
`updatedAt` CAS. A future need for durable idempotency records, explicit
revision numbers, or a pending state requires a new architecture review.

## 9. Failure and Rollback Behavior

| Condition | Behavior |
|---|---|
| Prepare response lost | Client retries prepare; an unused public ID may be abandoned; no secret or active database record exists. |
| Finalize response lost | Retry same `vaultId` and canonical payload; matching owner/payload returns safe replay success; mismatch conflicts. |
| Wrong master password | Client remains locked and shows generic `VAULT_UNLOCK_FAILED`; no server request with the password. |
| Tampered/malformed envelope | Reject structurally or fail authenticated unwrap; no downgrade, repair, or plaintext fallback. |
| Unsupported version/algorithm | Fail closed with typed validation/integrity error; do not mark verified. |
| Database failure before create | No active vault is reported; retry uses same resource identity. |
| Database failure after acceptance | Reconciliation fetch uses owner scope; no destructive collection rollback. |
| Concurrent finalization | At most one canonical create; matching replay is safe, divergent payload is `409`. |
| Stale metadata/key update | CAS returns conflict; client refetches and never overwrites newer state. |
| Cross-owner ID | Indistinguishable `404`; no envelope or timing-sensitive detail is intentionally returned. |
| Client lock/logout | Local key manager clears transient material; server envelope remains wrapped and unchanged. |

## 11. Updated G5.4.1 Acceptance Criteria

G5.4.1 may pass only if:

1. Server-generated MongoDB ObjectIds are allocated before client AAD creation;
   no ID is derived from password or key material.
2. Finalization is authenticated, owner-scoped, `_id`-unique, and cannot create
   a record for another owner.
3. No incomplete/pending/locked/unlocked server state is added; persisted
   state uses the approved existing enum.
4. `verified` is documented and tested as structural/client-preflight
   acceptance, never as server-side master-password verification.
5. Client unlock fetches only wrapped VEK metadata and performs KEK derivation
   and VEK unwrap locally with unchanged G5.3 exports.
6. Wrong passwords, wrong keys, tampering, malformed envelopes, and unsupported
   versions fail closed without secret disclosure.
7. Creation retries are safe using resource `_id` and canonical matching;
   divergent duplicate requests return conflict.
8. Metadata and wrapped-VEK updates require owner scope and CAS/ETag checks;
   stale requests cannot overwrite current key metadata.
9. No generic idempotency collection, Redis dependency, new index, or new
   schema state is introduced.
10. No raw key/password/plaintext secret enters MongoDB, API responses, logs,
    telemetry, browser persistence, Redux persistence, or query cache.
11. Legacy `/vault` operations continue returning
    `VAULT_ENCRYPTION_NOT_READY` until separately integrated and reviewed.
12. Tests cover API authorization, owner scoping, replay/concurrency, CAS,
    malformed/tampered envelope behavior, safe projections, and the no-server-
    unlock boundary.
13. Existing lint, test, build, and whitespace checks pass after implementation.
14. Security/Crypto Architect, Database Engineer, and independent Security
    Auditor review the actual implementation diff before gate closure.
