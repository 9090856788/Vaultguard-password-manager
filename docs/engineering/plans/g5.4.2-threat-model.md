# G5.4.2 VaultItem Threat Model

**Status:** Planning only

## Security Assumptions

- The access token has already passed G5.2 validation and identifies the user.
- The browser VEK is transient and is not trusted by the server as proof of
  identity.
- G5.3 AES-256-GCM and canonical AAD are the only approved crypto boundary.
- MongoDB is an untrusted persistence boundary for confidentiality claims;
  ciphertext integrity is authenticated, but availability remains a system
  concern.

## Threats and Mitigations

| Threat | Exposure | Target mitigation | Residual risk |
|---|---|---|---|
| IDOR | An attacker guesses an item ID | Every query includes owner, vault, item, and non-deleted predicates; safe 404 | Leaked valid IDs still require valid auth and owner |
| Cross-vault access | Item ID is combined with another vault path | Validate parent vault and use `ownerVaultItemScope` for every repository method | Operational bugs require integration tests |
| Cross-owner access | Client submits owner ID or another user's item | Derive owner from token only; never accept owner fields | Compromised account retains its own access |
| AAD substitution | Envelope is replayed under a different item/field/revision | Rebuild canonical AAD from server context and compare before persistence | A compromised client can submit valid ciphertext for its own data |
| Ciphertext swapping | One field's envelope is submitted for another | Field name is authenticated in AAD and envelope keys are allowlisted | A same-field replay is handled by revision/CAS |
| Replay | Old valid create/update is retried | Persisted lifecycle, revision CAS, and canonical replay comparison | Same-owner exact retries are intentionally idempotent |
| Stale overwrite | Concurrent clients update from old state | Mandatory If-Match and atomic revision predicate | Clients must reconcile 412 responses |
| Item ID substitution | Client changes ID after encryption | ID comes from persisted prepare and must match path, record, and AAD | Preparation records need bounded cleanup |
| Key ID substitution | Envelope claims a different key | Envelope keyId must equal AAD keyId and approved current context | Key rotation requires a later approved contract |
| Deleted-item access | Soft-deleted item remains addressable | Normal repository scopes include `deletedAt: null` and active state | Backups may retain deleted ciphertext |
| Category reference attack | Category from another vault is attached | Owner/vault/category lookup before write | Category deletion races require CAS/transaction policy |
| Plaintext logging | Request/error/activity pipeline records secrets | Strict validation, safe errors, redacted structured logs, safe events | Operators can still mishandle infrastructure logs |
| Oversized envelope | Large ciphertext causes memory/storage abuse | Bounded request body, field count, envelope lengths, and ciphertext size | Rate/resource limits need deployment tuning |
| Malformed crypto metadata | Parser or crypto downgrade path is abused | Exact version/algorithm/nonce/tag/AAD validation and fail-closed errors | New versions need explicit security review |
| Repository bypass | Generic create/update skips invariants | Narrow lifecycle repository API; code review and tests forbid direct model access | Future code can reintroduce bypass without review |
| Timing/error leakage | Different errors reveal ownership or tamper state | Safe 404/typed bounded errors and no secret values | Request timing is not perfectly uniform |
| Malicious category/content metadata | Metadata creates injection or abuse | Length, URL, tag, and character validation; no unsafe rendering assumptions | Frontend rendering remains a later gate |
| Malicious client | Authenticated client sends valid but harmful ciphertext | Server authenticates structure and authorization, not plaintext meaning | A compromised browser can encrypt attacker-chosen content |

## Security Evidence Required

The implementation gate must include tests for each authorization predicate,
all AAD dimensions, malformed/oversized envelopes, safe errors/logging,
concurrent CAS, replay, deletion, and repository method scope. Security audit
must inspect actual logs and HTTP responses, not only unit tests.

## Claims Boundary

G5.4.2 may claim only that the server validates and persists authenticated
encrypted envelopes under the approved contract after the implementation gate
passes. It may not claim that plaintext is impossible in the existing legacy
application, that all browser memory is zeroized, or that the product is
zero-knowledge/end-to-end encrypted before the full system audit.
