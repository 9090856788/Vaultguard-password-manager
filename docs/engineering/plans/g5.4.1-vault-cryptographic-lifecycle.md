# G5.4.1 Vault Cryptographic Lifecycle Plan

**Project:** VaultGuard Password Manager
**Branch:** `tech-stack-migration`
**Gate:** G5.4.1 - Vault Cryptographic Lifecycle
**Status:** Architecture and implementation plan only; no implementation is authorized by this document
**Planning agents:** Engineering Lead, Solution Architect, Security/Crypto Architect, Database Engineer, Backend Engineer, Technical Planner
**Prerequisites:** G3/G4 architecture, G5.1 database foundation, G5.2 backend authentication foundation, G5.3 crypto foundation, and the committed G5.3 security-auditor artifact

## 1. Purpose and Decision Summary

This plan defines the smallest implementation-ready slice for the vault
cryptographic lifecycle. It covers vault creation, client-side vault-key
initialization, server persistence of the authenticated wrapped VEK envelope,
client-side unlock, and lock/cleanup state transitions.

The server will never perform a Vault Master Password unlock. The target API
will return only owner-authorized wrapped VEK metadata and the KDF/envelope
metadata needed by the browser. The browser derives the KEK from the
Vault Master Password and unwraps the VEK locally with the existing G5.3
crypto foundation.

G5.4.1 does not enable VaultItem secret CRUD or any other encrypted-vault
feature. The existing `503 VAULT_ENCRYPTION_NOT_READY` boundary remains in
place for password, category, activity, audit, import/export, migration, and
other functionality until its own approved integration exists.

## 3. Scope

### Included

1. Create an empty or initialized vault record with client-produced wrapped
   VEK metadata.
2. Generate the VEK and derive the KEK in the browser/client.
3. Persist the wrapped VEK envelope and KDF metadata through the server.
4. List and fetch owner-authorized vault metadata.
5. Return wrapped key material only for owner-authorized client-side unlock.
6. Define browser-side unlock, lock, auto-lock, logout, and cleanup contracts.
7. Define vault key/version metadata validation and compare-and-set updates.
8. Add service, repository, API, integration, security, and lifecycle tests.

### Explicitly excluded

- VaultItem secret encryption or CRUD.
- Password, category, activity, audit, TOTP, import/export, or migration
  behavior.
- Legacy plaintext conversion or quarantine execution.
- Server-side Vault Master Password handling or VEK unwrapping.
- Frontend UI migration, Redux implementation, TanStack Query integration,
  React Router work, or CSS changes.
- Redis, Kafka, microservices, or new infrastructure.
- Key rotation execution. Metadata and future rotation boundaries may be
  represented, but rotation is a later approved lifecycle operation.

## 5. Data Model and Persistence Contract

Use the approved `vaults` collection and existing `IVault` shape. The server
persists only:

- `ownerUserId`, sourced from the authenticated access-token subject;
- bounded display `name`;
- `wrappedVekEnvelope`, containing the G5.3 authenticated envelope;
- `kdf`, containing approved Argon2id metadata and random salt;
- `currentKeyId`;
- `encryptionFormatVersion`;
- an approved lifecycle `migrationState` value;
- timestamps and optional soft-delete timestamp.

The server must reject or ignore client attempts to provide `ownerUserId`,
plaintext VEK, KEK, Vault Master Password, account password, plaintext vault
secrets, or undocumented fields. Mongoose `strict: 'throw'` remains the final
schema boundary.

The initial lifecycle state for a new vault should be `awaiting-owner` only
when the product requires a two-step owner verification. If creation already
includes a client-generated, locally verified wrapped VEK, the service may
persist the target state defined by the approved G4 transition. The exact
state transition must be fixed in the implementation contract before coding;
agents must not infer `verified` merely from a successful HTTP write.

For this slice, the recommended safe state is:

```text
create request accepted -> awaiting-owner
client unlock verification -> verified
```

The service must not claim that a vault is cryptographically verified until
the client has successfully unwrapped the VEK and completed the explicit
verification handshake described below.

Required indexes remain exactly the approved G4 indexes:

- `{ ownerUserId: 1, deletedAt: 1 }`
- `{ ownerUserId: 1, _id: 1 }`

No `{ host, vaultId }` uniqueness constraint or new speculative vault index is
introduced.

## 6. API Contract

The target route family is `/api/v1/vaults`. The current `/api/v1/vault`
legacy import/export routes remain behind `VAULT_ENCRYPTION_NOT_READY` and are
not repurposed by this plan.

### 6.1 `GET /api/v1/vaults`

- Authentication: required bearer access token.
- Request: no body; identity comes from validated `req.user.id`.
- Response: `{ items: [{ id, name, currentKeyId, encryptionFormatVersion,
  migrationState, createdAt, updatedAt }], nextCursor? }`.
- Sensitive material: no wrapped envelope, salt, KEK, VEK, master password,
  plaintext secret, or account secret in the list response unless the explicit
  client unlock fetch contract below is used for one selected vault.
- Authorization: return only active vaults owned by the authenticated subject.
- Errors: standard typed authentication, validation, and server errors; no
  cross-owner existence disclosure.

### 6.2 `POST /api/v1/vaults`

- Authentication: required bearer access token.
- Request shape:

```json
{
  "name": "Personal",
  "wrappedVekEnvelope": {
    "version": 1,
    "keyId": "key-uuid",
    "algorithm": "AES-256-GCM",
    "nonce": "base64url",
    "ciphertext": "base64url",
    "tag": "base64url",
    "aad": "base64url"
  },
  "kdf": {
    "algorithm": "Argon2id",
    "version": 1,
    "salt": "base64url",
    "memoryKiB": 65536,
    "timeCost": 3,
    "parallelism": 1,
    "outputBytes": 32,
    "purpose": "vault-kek"
  },
  "currentKeyId": "key-uuid",
  "encryptionFormatVersion": 1
}
```

- Sensitive material: the request contains only the wrapped VEK envelope and
  public cryptographic metadata. It must never contain the Vault Master
  Password, plaintext VEK, KEK, or plaintext vault data.
- Authorization: owner is taken from the access-token subject. Client
  `ownerUserId` is rejected, ignored, or overwritten with the authenticated
  identity; the implementation contract should choose rejection for strictness.
- Service checks: validate the exact G5.3 envelope, key ID, version, AAD
  purpose/context, nonce/tag sizes, and KDF metadata. The server does not
  unwrap the VEK and cannot validate the master password itself.
- Response: `{ item: { id, name, currentKeyId, encryptionFormatVersion,
  migrationState, createdAt, updatedAt }, revision? }`; do not echo the
  wrapped envelope unless required by the explicit response contract.
- Errors: `VALIDATION_ERROR`, `CRYPTO_ENVELOPE_INVALID`, `DUPLICATE_RESOURCE`
  only if a product uniqueness rule is approved, `UNAUTHORIZED`, and
  `INTERNAL_ERROR`. Error bodies contain no submitted secret material.

### 6.3 `GET /api/v1/vaults/:vaultId/key-material`

- Authentication: required bearer access token.
- Request: path `vaultId`; no master password or VEK in query/body.
- Response: owner-scoped `{ vaultId, wrappedVekEnvelope, kdf,
  currentKeyId, encryptionFormatVersion }`.
- Sensitive material: the wrapped VEK and salt are ciphertext/derivation
  metadata, not plaintext keys. The endpoint must not return a plaintext VEK,
  KEK, Vault Master Password, account verifier, or vault item data.
- Authorization: repository query must include both `vaultId` and
  `req.user.id`; missing owner match returns the same not-found result as an
  unknown vault.
- Errors: `401`, indistinguishable `404`, and typed malformed-persisted-data
  failure. A malformed stored envelope is a security/integrity error and must
  not be silently repaired or returned as usable data.

This is the approved client-side unlock endpoint. It returns the wrapped
envelope for local unwrap; it is not a server-side unlock endpoint.

### 6.4 `POST /api/v1/vaults/:vaultId/unlock-verification`

This endpoint is optional and should be implemented only if the product needs
an explicit server-visible state transition from `awaiting-owner` to
`verified`. If implemented:

- Authentication: required bearer access token.
- Request: `{ verification: <client-produced, non-secret proof> }` only if a
  separate approved protocol defines that proof. It must not contain the Vault
  Master Password, KEK, VEK, or plaintext secret.
- Response: `{ item: { id, migrationState: "verified", ... } }`.
- Authorization: owner-scoped compare-and-set transition from the expected
  current state and revision/timestamp.
- Errors: invalid proof/state returns a typed failure without revealing vault
  ownership or secret material.

No proof protocol is invented by this plan. If no approved proof is needed,
omit this endpoint and keep the server state at the lifecycle state selected
by the final product contract. A successful `GET key-material` or client
decrypt operation alone must never cause the server to claim verification.

### 6.5 Routes deliberately not enabled

There is no `POST /unlock` accepting a Vault Master Password, no server-side
VEK unwrap endpoint, no `GET` returning a plaintext key, and no endpoint that
accepts plaintext vault secrets in G5.4.1.

## 7. Service-Layer Design

`vaultLifecycleService` owns business rules and receives injected repository
and clock dependencies for deterministic tests. Controllers only validate
HTTP input, obtain `req.user.id`, call the service, and map typed errors.

Proposed service operations:

- `listVaults(ownerUserId, cursor, limit)`
- `createVault(ownerUserId, input)`
- `getVaultKeyMaterial(ownerUserId, vaultId)`
- `transitionVerification(ownerUserId, vaultId, expectedState, expectedRevision,
  proof)` only if the proof contract is approved
- `softDeleteVault(ownerUserId, vaultId, expectedRevision)` only if delete is
  explicitly included in the gate acceptance scope

The service must:

1. Reject invalid ObjectIds and bounded-input violations before repository use.
2. Derive owner identity exclusively from authenticated middleware.
3. Validate persisted/client envelope metadata against the G5.3 contract.
4. Enforce allowed lifecycle states and compare-and-set behavior.
5. Return safe DTOs, never raw Mongoose documents with sensitive fields.
6. Emit safe audit metadata only if the already-approved audit path is in
   scope; no secrets, envelope ciphertext, or passwords enter audit events.
7. Map cross-owner access to not-found behavior.
8. Preserve `VAULT_ENCRYPTION_NOT_READY` for out-of-scope operations.

## 8. Repository-Layer Design

Extend `VaultRepository` with explicit methods rather than exposing arbitrary
Mongoose updates:

- `listActiveForOwner(ownerUserId, pagination)` with safe list projection.
- `findKeyMaterialForOwner(vaultId, ownerUserId)` with only the approved
  wrapped envelope/KDF/key metadata projection.
- `createForOwner(input)` where owner is set by the service and schema
  validation is enabled.
- `transitionStateForOwner(vaultId, ownerUserId, expectedState,
  expectedUpdatedAt, update)` using owner scope and compare-and-set.
- `updateKeyMetadataForOwner(...)` retained only for approved metadata changes,
  with strict field allowlisting and validation.

Every query includes owner scope and `deletedAt: null` for active resources.
The repository must not provide an unscoped `findById` to the lifecycle service.
It must use `.lean()`/projection for responses and must not populate unrelated
secret-bearing resources.

A database transaction is not required for one-document creation if the final
contract has no dependent write. If creation also writes an audit event or
verification record, use the existing MongoDB transaction capability only
when the connection/test infrastructure supports it; otherwise define the
outbox or retry behavior before implementation. Do not introduce a new
collection in this gate solely to solve audit coupling.

## 9. G5.3 Crypto Integration Design

The implementation imports from `src/crypto/index.ts` and uses these existing
exports without copying or changing primitives:

```ts
const kdf = createKdfMetadata();
const kek = await deriveVaultKek(vaultMasterPassword, kdf); // client only
const vek = generateVek();                                  // client only
const wrapped = wrapVek(vek, kek, {
  vaultId,
  itemId: undefined,
  revision: 1,
  keyId,
  cryptoVersion: CRYPTO_VERSION,
  field: 'vek',
});
```

The pseudocode is a client-side contract illustration, not implementation.
The server receives only `wrapped` plus the public KDF metadata. For unlock,
the browser calls `deriveVaultKek(masterPassword, storedKdf)` and then
`unwrapVek(storedEnvelope, kek, context)`. The browser must call `zeroize()`
for temporary KEK/password-derived byte buffers as soon as practical, while
documenting JavaScript best-effort limitations.

The server may validate envelope shape and metadata using the same approved
validation contract, but it must not call `deriveVaultKek`, `unwrapVek`, or
receive the inputs required to do so. No crypto function changes, new
parameters, new envelope version, or new purpose is allowed in G5.4.1.

The wrap context is fixed and must agree on both sides:

```text
purpose = vek-wrap
vaultId = server-issued vault identifier
itemId = absent
field = vek
revision = lifecycle revision defined by the contract
keyId = currentKeyId
cryptoVersion = 1
```

If server-issued `vaultId` is required to bind creation AAD, the flow must be
two-phase: create a non-secret pending vault identity, return the ID, then let
the client wrap the VEK and finalize metadata with owner-scoped CAS. The first
phase must not create an apparently verified vault with missing key material.
The implementation team must choose this sequence explicitly before coding;
it must not use a client-generated untrusted ID as the authorization identity.

## 10. Vault Creation Sequence

The recommended sequence is a two-step client/server flow when the server ID
must be in AAD:

1. **Browser -> server:** authenticated `POST /vaults` with only bounded name
   and a creation intent, or a server-generated ID request. No master password
   or key material is sent.
2. **Server:** authorize the account, generate the MongoDB vault ID, set owner
   from the access-token subject, and persist a non-active pending record only
   if the schema/state contract supports it. No VEK is present yet.
3. **Server -> browser:** return the vault ID and non-secret creation metadata.
4. **Browser:** generate a random 32-byte VEK with `generateVek()`.
5. **Browser:** generate random per-vault KDF metadata with
   `createKdfMetadata()` and derive the 32-byte KEK from the Vault Master
   Password using `deriveVaultKek()`.
6. **Browser:** wrap the VEK with `wrapVek()` using the fixed `vek-wrap`
   AAD context, key ID, version, vault ID, and revision.
7. **Browser -> server:** authenticated finalize request containing only the
   wrapped envelope and approved KDF/key metadata.
8. **Server:** validate shape, exact approved parameters, envelope fields,
   owner scope, key ID/version agreement, and expected lifecycle state.
9. **Server -> database:** persist the wrapped envelope and metadata with an
   owner-scoped compare-and-set update.
10. **Server -> browser:** return safe vault metadata. Never return the VEK.
11. **Browser:** locally unwrap the VEK with the KEK, verify it is exactly
   32 bytes, and retain it only in the approved transient key manager. If the
   contract requires a verified state, send only the separately approved
   non-secret verification proof.

If the implementation can allocate a stable server ID before the first
request and include it in the client context, a one-request create flow may
be used, but the server must still control the persisted `_id` and owner.
The chosen flow must be covered by a documented sequence test.

## 11. Vault Unlock Sequence

### Browser/client

1. Obtain an access token through the existing G5.2 authentication flow.
2. Request `GET /vaults/:vaultId/key-material`.
3. Server returns the owner-authorized wrapped envelope and KDF metadata.
4. Prompt for the Vault Master Password locally. Do not place it in a request,
   URL, Redux persistence, browser storage, telemetry, or logs.
5. Derive the KEK with the stored, validated KDF metadata.
6. Call `unwrapVek()` with the fixed context.
7. On success, verify the returned VEK is exactly 32 bytes and place it only
   in a transient in-memory key manager. Do not persist it in localStorage,
   sessionStorage, IndexedDB, Redux persistence, TanStack Query cache, or
   error reports.
8. Clear temporary KEK and password-derived buffers as soon as practical.

### Server

- Authenticate and authorize the request.
- Fetch the envelope and metadata through an owner-scoped repository method.
- Return the wrapped envelope only.
- Never derive a KEK, unwrap a VEK, receive the Vault Master Password, or
  inspect vault plaintext.

### Database

- Store only the wrapped envelope and approved public KDF/key metadata.
- Never store a raw key or password.
- Do not update verification state merely because the metadata was fetched.

There is no server-side unlock operation. A wrong master password, wrong KEK,
or tampered envelope is detected by the browser's authenticated unwrap and is
reported as a generic unlock failure without sending the password or key to
the server.

## 12. Vault Lock and Key Lifecycle

At this stage, "lock" means the client vault key manager has no usable VEK and
all client code requiring an unlocked vault refuses to operate. It does not
mean deleting or rotating the persisted wrapped envelope.

Lock is triggered by explicit user lock, logout, access-session invalidation,
auto-lock timeout, tab/window lifecycle policy, or an unrecoverable unlock
failure. The client must:

- zeroize and discard transient VEK/KEK buffers where possible;
- clear decrypted plaintext and pending crypto work queues;
- clear key references from Redux and query cache if any non-persistent
  handles were used;
- cancel vault-secret requests and prevent stale responses from repopulating
  state;
- clear sensitive error/telemetry context;
- avoid claiming cryptographic erasure of historical JavaScript memory.

The server does not receive a raw key on lock and does not need a lock API for
local cleanup. A future server session-revocation or audit event may be a
separate approved operation, but it must not be confused with local key lock.

## 13. State Machine and Metadata Rules

The lifecycle state machine is:

```text
pending/creation-intent -> awaiting-owner -> verified
                                  \-> blocked
active verified -> blocked      (integrity or verification failure)
active state -> deleted          (separate approved owner-scoped operation)
```

The exact `pending` representation must use an existing approved state or be
escalated before implementation; the current schema does not list `pending`.
The safer first implementation may avoid a persisted pending state by using a
server-generated ID endpoint that does not write a vault until finalization.

Metadata invariants:

- `wrappedVekEnvelope.keyId === currentKeyId`.
- Envelope version and `encryptionFormatVersion` are supported and agree with
  the approved contract.
- KDF fields equal the locked Argon2id baseline.
- Salt is random, canonical, and per-vault.
- Envelope AAD is the canonical G5.3 AAD for the same vault/key/revision
  context.
- `ownerUserId` is immutable and sourced only from authenticated identity.
- State transitions are allowlisted and compare-and-set protected.

## 14. Failure, Transaction, and Rollback Behavior

| Failure | Required behavior |
|---|---|
| Empty/invalid master password | Client rejects before crypto; no request is made; no secret is logged. |
| Wrong master password/wrong KEK | `unwrapVek()` fails closed locally; generic unlock failure; no server retry with password. |
| Malformed envelope | Server rejects on write or returns typed integrity failure on read; no repair or fallback. |
| Tampered envelope/AAD/tag | Authenticated unwrap fails; client remains locked; audit/telemetry contains safe metadata only. |
| Unsupported crypto version/algorithm | Reject at API and crypto boundaries; never downgrade. |
| Database write failure | Finalization returns failure; client retains no authoritative state and may retry idempotently with the same request ID if approved. |
| Duplicate create request | Use an idempotency key only if the existing API contract approves it; otherwise return a typed conflict and do not create a second vault. |
| Duplicate vault names | Do not invent uniqueness. Allow multiple names unless product approval adds a constraint. |
| Unauthorized vault access | Return indistinguishable not-found; never return envelope metadata. |
| CAS/state conflict | Return conflict; client refetches safe metadata and does not overwrite newer state. |
| Client crash before finalize | No persisted plaintext or raw key; any server-created pending identity remains non-active and requires controlled cleanup. |
| Finalize succeeds, local unwrap fails | Vault remains non-verified/blocked according to the state contract; client cannot claim unlock; support must not request the master password. |

No destructive rollback deletes all collections. Rollback is limited to the
single staged vault lifecycle write, owner-scoped state restoration where
supported, and retention of audit evidence. Envelope version gating prevents
plaintext fallback or downgrade.

## 15. Server/Client Trust Boundary

The server is trusted to authenticate the account, authorize ownership, and
store ciphertext/metadata, but it is not given the Vault Master Password or
plaintext VEK. The client is responsible for deriving and unwrapping the VEK
and later decrypting secret fields. This supports the approved client-side
encryption target but does not by itself establish a production zero-knowledge
claim; the full client, browser, deployment, and threat model must pass later
gates.

Server-visible values are limited to account identity, vault metadata, wrapped
VEK envelope, KDF metadata, key ID, version, timestamps, lifecycle state, and
request/security metadata. Do not log ciphertext or AAD unnecessarily, and
never log passwords, raw keys, plaintext, tokens, or full request bodies.

## 16. Threat Model

| Threat | Current exposure | Target mitigation in G5.4.1 | Residual risk |
|---|---|---|---|
| Server compromise | Current legacy routes and JSON store are not a finished encrypted vault. | Keep master password/VEK client-side; server persists only wrapped VEK and metadata; preserve 503 boundary. | Compromised server can serve malicious client code or alter ciphertext; later client integrity/deployment review remains required. |
| Database compromise | Target database foundation exists, but lifecycle integration is absent. | Store only authenticated wrapped envelope and public KDF metadata; owner-scoped reads; no raw keys. | Offline password guessing remains possible against wrapped VEK; Argon2 benchmarking and password policy remain conditions. |
| Malicious authenticated user | Authenticated user could request arbitrary IDs. | Derive owner from access token; repository scope includes owner and vault ID; indistinguishable not-found. | A user can access their own authorized vaults; account compromise is outside this control. |
| Cross-vault access | Legacy code is JSON-backed and not the target lifecycle. | Owner/vault-scoped repository methods and AAD vault binding. | Implementation defects or future unscoped methods require IDOR testing and review. |
| Accidental plaintext leakage | Legacy `PasswordItem` and import/export contain plaintext behavior, but remain gated. | No lifecycle plaintext fields; strict request validation; 503 remains for out-of-scope routes. | Legacy code still requires later migration/integration remediation before production. |
| Browser storage leakage | No lifecycle key manager currently exists. | Keep KEK/VEK/password transient; no localStorage/sessionStorage/IndexedDB/Redux/query persistence. | XSS or malicious extensions can access an unlocked browser; CSP and browser security review remain required. |
| Logging/telemetry leakage | Existing app has request logging and legacy flows. | Safe DTOs, redaction, no secret-bearing errors/audit events, no raw envelope logging. | Operational tooling and third-party extensions need downstream verification. |
| Replay/race conditions | Repository has timestamp CAS for key metadata; lifecycle API is absent. | Idempotency/state/CAS design, atomic owner-scoped transitions, concurrent finalize tests. | Distributed retries and multi-tab coordination need integration tests. |

## 17. Test Plan

### Unit tests

- Request validation rejects missing/extra sensitive fields, invalid IDs, bad
  names, unsupported versions/algorithms, wrong KDF parameters, malformed
  base64url, wrong nonce/tag sizes, and key ID mismatch.
- Service maps authenticated owner identity into repository input and never
  trusts body `ownerUserId`.
- Safe DTOs exclude envelope data from list responses and exclude passwords,
  KEKs, VEKs, and master passwords everywhere.

## 18. G5.3 Compatibility

## 21. Risks and Open Questions

1. **Server-issued ID versus one-request creation:** AAD binds `vaultId`, so
   the implementation contract must choose a stable server-ID sequence before
   coding. Recommended resolution: server-generated identity followed by
   client wrapping and owner-scoped finalize, without an active verified record
   before finalization.
2. **Lifecycle state vocabulary:** the current schema has no `pending` state.
   Product/architecture owners must approve whether to use an existing state,
   avoid persistence until finalization, or add a versioned schema state.
3. **Verification handshake:** the G4 state model includes `verified`, but no
   proof protocol is approved. Do not invent a proof or claim verification
   without explicit approval.
4. **Creation idempotency:** decide whether an idempotency key is part of the
   API contract. Do not silently add a new persistence field or collection.
5. **Audit coupling:** decide whether vault lifecycle audit events are in this
   gate or a later approved integration. Do not add an outbox collection solely
   for this feature.
6. **Browser key manager owner:** frontend architecture must approve the
   transient in-memory owner and multi-tab cleanup mechanism before client
   unlock integration. No raw-key persistence is acceptable while deciding.
7. **`/vault` to `/vaults` transition:** confirm whether the legacy route stays
   mounted only for 503 compatibility or receives a deprecation response. The
   target contract is `/vaults`.

## 22. Acceptance Criteria

1. The approved G5.4.1 route/service/repository files exist and follow
   route -> controller -> service -> repository -> Mongoose.

8. Lock/logout/auto-lock contracts remove transient client key material and do
   not persist it in browser storage, Redux persistence, or query cache.
