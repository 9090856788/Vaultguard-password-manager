# G5.4.2 Contract Resolution

**Status:** Contract resolution approved; implementation remains a separate gate

**Approval record:** The five decisions in section 6 were approved by the
project owner on 2026-09-10. This records contract approval only; it does not
authorize source-code implementation or a commit.

## 1. Resolved Decisions

| Area | Decision | Reason |
|---|---|---|
| Item identifier | Server-generated MongoDB ObjectId from persisted prepare | Client needs the ID for AAD and arbitrary IDs must not be accepted |
| Preparation storage | Existing `vaultItems` collection with `lifecycleState: preparing` | Avoids a new collection and binds the ID to owner and vault |
| Owner | Authenticated access-token subject | Client owner fields are untrusted |
| Parent vault | Must be owner-scoped, non-deleted, and `verified` | Prevents cross-owner/cross-vault use |
| Secrets | Client-side AES-256-GCM envelopes only | Preserves G3/G5.3 boundary |
| KDF/VEK | Existing G5.3 contract; no server derivation or unwrap | No custom cryptography or server key exposure |
| Secret AAD | `purpose, vaultId, itemId, field, revision, keyId, cryptoVersion` | Binds ciphertext to its exact resource and revision |
| Initial revision | `1` | Matches existing revision contract |
| Updates | Strict `If-Match`/revision CAS; no last-write-wins | Prevents stale encrypted overwrite |
| Soft delete | Owner-scoped CAS; normal reads exclude deleted records | Preserves G4 soft-delete model |
| Plaintext inputs | Rejected at every VaultItem endpoint | Server never receives vault secrets |
| Search | Metadata filters only; secret search is client-side | Avoids plaintext/ciphertext search leakage |
| History | Not implemented in G5.4.2; a separately approved encrypted history collection is the later target | G4 requires history, but no silent new collection is allowed |
| Permanent delete | Operational policy only, not a normal endpoint | Avoids false cryptographic-erasure claim |

## 2. Exact Request Allowlists

### Prepare

Only `metadata` is accepted. `metadata` contains only:
`title`, `websiteUrl`, `categoryId`, `tags`, `colorLabel`, `websiteLogo`,
`isFavorite`, and `isPinned`.

### Finalize create

Only `itemId` and `encryptedSecrets` are accepted. `encryptedSecrets` keys are
only the approved secret field names, and each value is the exact G5.3
envelope shape. Top-level plaintext fields are forbidden.

### Update

Only `metadata` and `encryptedSecrets` are accepted. When encrypted secrets
are supplied, the complete approved encrypted-secret object is required for
the initial implementation.

### Queries and headers

Only documented bounded filters are accepted. `If-Match` is mandatory for
finalize, update, delete, and restore. Unknown query parameters and malformed
revision values are rejected.

Every allowlist rejection uses a generic error message and never interpolates
the rejected key's value.

## 3. Envelope and AAD Contract

The client calls the existing G5.3 `encryptSecret()` once per secret field.
The envelope is version `1`, algorithm `AES-256-GCM`, key identified by
`keyId`, with a fresh 12-byte nonce, 16-byte tag, canonical base64url fields,
and canonical length-delimited AAD. The server validates structure and AAD but
never decrypts.

AAD field ordering is inherited exactly from G5.3:

```text
VaultGuard-AAD
cryptoVersion
purpose
vaultId
itemId
field
revision
keyId
```

`purpose` is `vault-secret` for VaultItem fields. Any absent, extra, changed,
or unsupported context fails closed.

## 4. Revision Contract

The preparation response establishes revision `1`. Finalization requires that
revision and atomically moves `preparing` to `active`. The first update
expects `If-Match: 1`, authenticates its new envelopes against revision `2`,
and increments the stored revision to `2`. Subsequent writes repeat the same
sequence. Delete and restore also increment revision, but do not rewrite
encrypted content.

A stale request receives `412 VAULT_ITEM_VERSION_CONFLICT`. A matching retry
may return the existing safe record with `replay: true`; a divergent retry
receives a conflict. No last-write-wins behavior is permitted.

## 5. Preparation and Finalization Contract

The server-issued item ID is enforceable because preparation writes:

```text
{ _id, vaultId, ownerUserId, metadata, lifecycleState: 'preparing', revision: 1 }
```

It writes no encrypted or plaintext secret fields. Finalization requires the
same ID, owner, vault, `preparing` state, revision, and valid envelope AAD.
The atomic update writes the encrypted envelopes and transitions to `active`.
An arbitrary ObjectId, another owner's ID, an item in another vault, or an
already deleted item is rejected.

## 6. Approved Contract Decisions

1. Add `lifecycleState` to the VaultItem schema and make `encryptedSecrets`
   conditionally required while the record is `preparing`.
2. Use the exact server-visible metadata and encrypted-secret field sets
   defined in this package.
3. Include owner-scoped restore in G5.4.2, protected by `If-Match`/revision
   CAS. Restore changes lifecycle state only and never rewrites secrets.
4. Retain the G4 requirement for a future separate encrypted history
   collection with 90-day initial retention. The collection is approved as a
   later architecture unit, but is explicitly out of G5.4.2 implementation.
5. Retain `websiteLogo` as bounded public metadata, validated as an approved
   URL form and never treated as a secret field.

No implementation agent may alter these approved decisions by silently
changing models, collections, indexes, or endpoint semantics.

## 7. Rejected Alternatives

- Client-generated item IDs: rejected because the client would control an AAD
  identifier and server-issued resource contract would be lost.
- Non-persisted prepare IDs: rejected because arbitrary IDs could be finalized.
- Server-generated ID only during final POST: rejected because the client
  cannot bind AAD to the final ID before encryption.
- Server-side master-password or VEK processing: prohibited by G3.
- Plaintext secret fields beside `encryptedSecrets`: prohibited by G4.
- Last-write-wins updates: rejected because stale clients could overwrite
  encrypted data and break revision/AAD binding.
- New preparation collection: rejected unless the existing VaultItem lifecycle
  extension proves technically impossible and receives separate approval.
- Embedded unbounded history array: rejected due to document growth and 90-day
  retention control problems.
