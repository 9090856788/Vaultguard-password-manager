# G5.4.2 VaultItem Encryption Lifecycle

**Status:** Contract resolution approved; implementation not authorized yet

**Scope:** Encrypted VaultItem CRUD after G5.4.1

**Baseline:** G3 security baseline, G4 database architecture, G5.3 crypto
foundation, and committed G5.4.1 vault lifecycle

## 1. Gate Boundary

G5.4.2 integrates the existing G5.3 primitives with VaultItem persistence. It
does not add cryptographic primitives, change KDF parameters, accept a Vault
Master Password, unwrap a VEK on the server, or enable unrelated password,
TOTP, import/export, migration, Redux, TanStack Query, Redis, or UI work.

The server receives only authenticated identity, public metadata, and
authenticated encrypted envelopes. The browser performs master-password
input, KEK derivation, VEK unwrap, plaintext encryption, and plaintext
decryption.

No zero-knowledge, end-to-end-encryption, encrypted-at-rest, or encrypted
export claim is approved by this plan.

## 2. Selected VaultItem Lifecycle

The existing `vaultItems` collection remains the only persistence location.
The implementation must add an explicit lifecycle field before implementation:

```ts
lifecycleState: 'preparing' | 'active' | 'deleted'
```

The existing target fields remain unchanged, with these controlled additions:

- `lifecycleState`, required, indexed only where approved;
- `encryptedSecrets` optional only while `lifecycleState === 'preparing'`;
- `deletedAt` set only for `deleted` records.

This schema extension has been approved at the contract-resolution gate and
still requires a synchronized G4 database document update before implementation.
It is the smallest safe way to persist a server-issued item
ID before the client constructs AAD. No second preparation collection is
permitted.

Transitions:

```text
preparing -> active       successful encrypted create
preparing -> preparing    retry with the same server-issued ID and payload
active -> active          metadata or encrypted-secret CAS update
active -> deleted         owner-scoped soft delete with CAS
deleted -> active         owner-scoped restore with CAS
deleted -> purged         explicit operational retention process only
```

Preparation records contain server-visible metadata only. They contain no
`encryptedSecrets`, plaintext secret, KEK, VEK, or master-password field.
Reads and lists exclude `preparing` records unless an explicit owner-scoped
reconciliation endpoint is approved. Deleted records are excluded from normal
reads and lists.

## 3. Ownership and Vault Relationship

Every operation derives `ownerUserId` from the authenticated access-token
identity. Client-supplied owner IDs are rejected. Every repository predicate
must include both `ownerUserId` and `vaultId`; item ID alone is never an
authorization check.

Before creating or reading an item, the service verifies that the parent vault
exists, belongs to the authenticated owner, is not deleted, and is in the
approved `verified` state. A category must be absent or belong to the same
owner and vault and be active. Cross-vault and cross-owner references return a
safe not-found or validation error without revealing which condition failed.

## 4. Item ID and AAD Ordering

The selected contract uses a persisted prepare step:

1. Client sends server-visible metadata to `POST /api/v1/vaults/:vaultId/items/prepare`.
2. Server authenticates the owner, validates the parent vault and metadata,
   allocates a MongoDB ObjectId, and persists a `preparing` VaultItem.
3. Server returns the ObjectId and revision `1`.
4. Client constructs AAD with the exact returned item ID, vault ID, field,
   revision, key ID, and crypto version, then encrypts each secret-bearing
   field with the VEK.
5. Client sends the item ID and encrypted envelope(s) to the finalize create
   endpoint.

The server never constructs a substitute AAD from plaintext and never receives
the VEK. The server validates that every envelope's authenticated AAD matches
the request path, persisted item ID, field scope, expected revision, key ID,
and supported version.

## 5. Encryption Contract

`encryptedSecrets` is an object keyed only by an approved field allowlist. A
field envelope has the existing G5.3 shape:

```ts
{
  version: 1,
  keyId: string,
  algorithm: 'AES-256-GCM',
  nonce: string,       // canonical base64url, 12 decoded bytes
  ciphertext: string,  // canonical base64url, bounded size
  tag: string,         // canonical base64url, 16 decoded bytes
  aad: string          // canonical base64url
}
```

The initial approved secret field set is `username`, `password`, `notes`,
`totp`, and `recoveryCodes`, subject to product confirmation. The object may
not contain unknown fields. Each field is encrypted independently with
`encryptSecret()` and the same VEK, using a fresh nonce and this context:

```ts
{
  purpose: 'vault-secret',
  vaultId,
  itemId,
  field: '<approved secret field name>',
  revision,
  keyId,
  cryptoVersion: 1
}
```

Empty optional secrets are represented by an encrypted value or an explicitly
approved omission; the server never interprets either as plaintext. The server
stores envelopes as received after strict structural and AAD validation. It
does not decrypt, normalize, search, compare, or log ciphertext contents.

## 6. Revision and CAS Contract

- Initial preparation revision: `1`.
- Finalize create accepts only revision `1` and transitions `preparing` to
  `active` atomically.
- Every metadata or encrypted-secret update requires `If-Match` containing the
  current revision and increments revision by exactly one.
- The resulting revision is the revision authenticated in the new envelopes.
- The atomic update predicate includes `_id`, `vaultId`, `ownerUserId`,
  `lifecycleState`, `deletedAt`, and `revision`.
- A stale revision returns `412 VAULT_ITEM_VERSION_CONFLICT`; last-write-wins
  is prohibited.
- Delete and restore also use revision CAS and increment revision.

For retries, a create or update with the same owner, item, revision, and
canonical envelope/metadata payload may return the already persisted safe
resource with an explicit replay indicator. A divergent payload returns a
conflict. No raw request body or plaintext fingerprint is persisted for
idempotency.

## 7. API Contract

All endpoints require authentication and a verified parent vault.

### Prepare

`POST /api/v1/vaults/:vaultId/items/prepare`

Request:

```json
{
  "metadata": {
    "title": "Example",
    "websiteUrl": "https://example.test",
    "categoryId": "optional-object-id",
    "tags": [],
    "colorLabel": "optional",
    "websiteLogo": "optional-url",
    "isFavorite": false,
    "isPinned": false
  }
}
```

Response `201`:

```json
{
  "itemId": "server-issued-object-id",
  "vaultId": "vault-object-id",
  "revision": 1,
  "lifecycleState": "preparing"
}
```

### Finalize create

`POST /api/v1/vaults/:vaultId/items`

Request:

```json
{
  "itemId": "server-issued-object-id",
  "encryptedSecrets": {
    "username": { "version": 1, "keyId": "key-1", "algorithm": "AES-256-GCM", "nonce": "...", "ciphertext": "...", "tag": "...", "aad": "..." },
    "password": { "version": 1, "keyId": "key-1", "algorithm": "AES-256-GCM", "nonce": "...", "ciphertext": "...", "tag": "...", "aad": "..." }
  }
}
```

The request must not repeat metadata; the persisted preparation is canonical.
The server requires `If-Match` for the preparation revision and returns the
safe item metadata plus envelopes. A retry with the same payload is `200` with
`replay: true`; a divergent or unprepared ID is rejected.

### Read and list

- `GET /api/v1/vaults/:vaultId/items` returns owner-scoped active items with
  metadata and encrypted envelopes. It supports only approved bounded filters
  such as `categoryId` and `favoriteOnly`; it never accepts secret search.
- `GET /api/v1/vaults/:vaultId/items/:itemId` returns one owner-scoped active
  item with the same safe shape.

### Update

`PATCH /api/v1/vaults/:vaultId/items/:itemId` requires `If-Match`. The body
must contain one or both of:

```json
{
  "metadata": { "title": "...", "tags": [] },
  "encryptedSecrets": { "password": { "...": "..." } }
}
```

Metadata-only updates do not change secret envelopes and do not require a new
VEK operation. Any encrypted-secret update must use envelopes whose AAD binds
the resulting revision. Partial secret updates are allowed only if the server
has an approved merge contract; otherwise the client sends the complete
encrypted secret object to avoid ambiguous revision binding. The initial
implementation should require the complete encrypted secret object whenever
`encryptedSecrets` is present.

### Delete and restore

- `DELETE /api/v1/vaults/:vaultId/items/:itemId` requires `If-Match`, performs
  owner-scoped soft delete, and returns the new revision.
- Restore is included in G5.4.2. Use
  `POST /api/v1/vaults/:vaultId/items/:itemId/restore` with `If-Match`; it
  must not decrypt or rewrite secrets.
- Permanent delete is not a normal API operation in G5.4.2. It remains an
  operational retention action with separate approval.

## 8. Strict Validation

Every request uses an exact allowlist and bounded values. Unknown fields are
rejected with a generic typed validation error. Error messages never contain
submitted values.

Prepare accepts only `metadata`, and metadata accepts only the approved public
metadata fields. Finalize accepts only `itemId` and `encryptedSecrets`. Update
accepts only `metadata` and `encryptedSecrets`. Query parameters accept only
the documented bounded filters. Path IDs and `If-Match` values are validated.

The following are always rejected when supplied outside the envelope contract:
`password`, `username`, `notes`, `totp`, `recoveryCodes`, `secret`,
`plaintext`, `masterPassword`, `vaultMasterPassword`, `kek`, `vek`, and
arbitrary unknown fields. A `username` is rejected as a top-level or metadata
field because it is secret-bearing in this contract.

Envelope validation rejects unknown envelope fields, unsupported versions or
algorithms, non-canonical encodings, invalid nonce/tag sizes, oversized
ciphertext, missing fields, key ID mismatches, and AAD mismatches.

## 9. Repository and Service Boundaries

The flow remains:

```text
route -> controller -> service -> repository/model -> MongoDB
```

Required repository methods are owner/vault scoped:

- `prepareForOwner`
- `findByIdForOwner`
- `listForOwner`
- `finalizePreparedForOwnerWithCas`
- `updateForOwnerWithRevision`
- `softDeleteForOwner`
- `restoreForOwner`

Read projections must be explicit. Repository methods that accept unscoped
IDs or arbitrary update documents are not allowed for lifecycle paths. The
existing generic `create()` bypass should be removed, narrowed, or made
internal before implementation so a future controller cannot bypass owner,
vault, lifecycle, and encryption checks.

## 10. Categories and Events

Category validation is owner- and vault-scoped. A deleted or cross-vault
category is invalid. Category IDs are metadata and are never included in
secret AAD.

Safe activity events may include `item.created`, `item.updated`,
`item.deleted`, `item.restored`, and `item.tamper_detected`. Audit events may
record resource type/ID, vault ID, actor, outcome, request ID, and a bounded
reason code. They must not include request bodies, envelope fields, ciphertext,
plaintext, keys, passwords, or secret field names where that would reveal
sensitive behavior.

## 11. History Decision

G4 requires encrypted version history with an initial 90-day retention. The
current VaultItem envelope cannot hold an unbounded history safely, and adding
an array would create document growth and retention problems. A separate
encrypted history collection is therefore the technically preferred design,
but it is a new collection and is not authorized by this plan alone.

G5.4.2 must retain only the current encrypted envelope and revision. It must
not claim version-history support or silently add a `vaultItemHistory`
collection. A follow-up architecture decision must approve the collection,
indexes, retention/TTL behavior, ownership predicates, and envelope/AAD
contract before history implementation.

## 12. Rollback and Failure Handling

Validation occurs before any write. Finalize uses one atomic conditional update;
there is no partial transition to active. If a deployment is rolled back,
existing `preparing` records remain inert and can be reconciled or expired by
an approved operational process. Active encrypted records remain readable by
the previous compatible implementation because the G5.3 envelope is
versioned. No rollback deletes collections or decrypts/re-encrypts data.

If a new implementation cannot validate an existing envelope version, it must
fail closed and preserve the record for a later compatible release.

## 13. Security and Error Model

Use typed safe errors: `VAULT_ITEM_INVALID_REQUEST`,
`VAULT_ITEM_NOT_FOUND`, `VAULT_ITEM_AUTHORIZATION_FAILED`,
`VAULT_ITEM_VERSION_CONFLICT`, `VAULT_ITEM_ENVELOPE_INVALID`,
`VAULT_ITEM_CRYPTO_UNSUPPORTED`, `VAULT_ITEM_TAMPERED`,
`VAULT_ITEM_CATEGORY_INVALID`, and `VAULT_ITEM_PREPARATION_REQUIRED`.

Responses must not distinguish another owner's existence from a missing item
where that would create an IDOR oracle. Tamper and malformed envelope errors
are safe, bounded, and contain no envelope contents. No crypto material is
logged; structured logs contain request ID, route, status, and reason code
only.

## 14. Implementation Sequence

1. Record the approved `preparing` lifecycle schema extension and API
   contract, then synchronize the G4 database documentation. The approved
   future history collection remains outside this implementation scope.
2. Update G4 database/schema/index documentation and the G5 condition register.
3. Narrow repository methods and remove generic lifecycle bypasses.
4. Add model validation for lifecycle-dependent encrypted fields and bounded
   envelope sizes; preserve approved indexes.
5. Add strict validation and safe error mapping.
6. Implement owner/vault/category service checks and atomic CAS methods.
7. Implement routes/controllers with no direct database access.
8. Add unit, repository, HTTP, concurrency, tamper, and authorization tests.
9. Run focused tests, full tests, lint, build, and diff checks.
10. Obtain database-engineer, backend-engineer, QA, security-crypto-architect,
    security-auditor, code-reviewer, and engineering-lead gates before any
    commit or G5.4.3 planning.

## 15. Implementation Authorization

**G5.4.2 status: READY FOR IMPLEMENTATION PLANNING, NOT IMPLEMENTATION.** The
five contract decisions are approved. Source implementation must wait for the
separate engineering-lead implementation authorization, synchronized G4
documentation, and specialist pre-implementation review. Encrypted history
remains approved as a later architecture unit but is out of G5.4.2 scope.
